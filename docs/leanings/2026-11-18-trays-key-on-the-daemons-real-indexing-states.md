# 2026-11-18 — Trays now key on the daemon's real indexing states

- **Status:** Resolved
- **Task/context:** Resolves [Both trays wait for an "indexing" repository state the daemon never writes](2026-11-18-trays-wait-for-an-indexing-state-the-daemon-never-writes.md), which was recorded as Open during the macOS tray latency fix.
- **Unexpected observation or failure:** Neither tray ever showed indexing. A repository the daemon reported as `updating` was labelled "Ready (7 files)", the headline read "Status: Ready (Idle)", and the macOS item kept its idle icon. The Linux tray also labelled a `queued` repository "Ready".
- **Evidence:** Before the fix, the new contract test `packages/coding-agent/test/indexing-tray-repository-states.test.ts` failed for both trays. The compiled Swift logic returned `{ isIndexing: false, toolTip: "P Code Indexing (Idle)" }`, "Status: Ready (Idle)" and "Ready (7 files)" for an `initializing` repository. The Python tray returned "  Status: Ready (Idle)" and "Ready (7 files)" for an `updating` repository with `progress.phase: "indexing"`. The existing tray tests passed only because their fixtures used the invented `"indexing"` state.
- **Approaches tried:**
  - **Attempt:** Have the daemon write `"indexing"`.
    - **Outcome:** Did not work (rejected)
    - **Why:** `RepositoryServiceStatus.state` reuses `RagState`, which the footer, `/index` and semantic search already read. A tray-only state name would split that contract.
  - **Attempt:** Add an explicit `active` flag to the status file.
    - **Outcome:** Did not work (rejected)
    - **Why:** It would change the producer and the status schema for information the state already carries. The daemon sets `initializing` or `updating` when the drain worker picks a repository and on every progress report, and leaves those states only when the refresh ends.
  - **Attempt:** Map `initializing` and `updating` to the indexing presentation in both trays, and decide the progress text by `progress.phase`.
    - **Outcome:** Worked
    - **Why:** The state alone decides whether a repository is indexing. Progress is absent until the first report, so keying on progress would miss the start. The phase matters only for the text: `preparing` can report 100% before any chunk is embedded (`rebuild.ts`) and `finalizing` restarts at 0%, so the trays show a percentage only in the `indexing` phase and name the other phases, as the footer already does.
- **Root cause:** The tray contract was written against a state name that `RepositoryServiceStatus` does not contain, and the fixtures were hand-written strings, so tests checked the trays against themselves rather than against the daemon.
- **Resolution:** `status_headline.swift` (`isRepoIndexing`, `indexingProgressLabel`) and `indexing_tray_status.py` (`is_repo_indexing`, `indexing_progress_label`, `tooltip_text`) map `initializing`/`updating` to indexing. The Linux fallback tooltip moved into the testable `tooltip_text`, and the Linux repository label gained `Queued`. `packages/coding-agent/test/indexing-repository-service-states.ts` lists every daemon state and progress phase. Type-checking fails if `RepositoryServiceStatus` gains a value that the list lacks, and `trayStatus()` accepts only real states.
- **Verification:** The contract test runs every daemon state and phase, percent boundaries, progress without a phase, and a mixed multi-repository status through the compiled Swift logic and the Python logic. All eight of its tray cases fail against the pre-fix sources and pass after the fix; the updated macOS tray tests behave the same way. The Python unit tests pass, the full Swift tray compiles, and it starts cleanly against a synthetic `updating` status file. The live menu-bar item was not inspected: it sat in the menu-bar overflow and is not exposed to accessibility. In CI, where only Linux runs and the Python unit tests are not part of the run, the contract test's Python half fails instead of skipping when `python3` is missing.
- **Prevention/follow-up:** Tray fixtures take `RepositoryServiceState`, so `npm run check` rejects an invented state. Both trays still label `stale`, `partial`, `not_initialized`, `unavailable` and `disabled` as "Ready"; that is a separate presentation decision.
- **Reusable learning:** Test a status consumer against an enumeration that the type checker ties to the producer's type. Hand-written fixture strings only prove that the consumer agrees with itself.
