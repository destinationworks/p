# 2026-11-21 — A reinstalled tray binary left the old macOS tray running

- **Status:** Resolved
- **Task/context:** Installing a branch that added CPU, memory and GPU rows to the macOS indexing tray menu. Since #193 the tray runs as its own per-session launchd job (`com.dst.p.code-index-tray.<hash>`, `ProcessType` `Interactive`, no `KeepAlive`), defined by a plist in `~/.p/agent/indexing-service/` that the daemon writes and kickstarts at start, at each five-minute reconcile and on config changes.
- **Unexpected observation or failure:** After `./reinstall.sh` the menu bar still showed the old menu. The new rows appeared only after a manual `launchctl kickstart -k gui/$UID/com.dst.p.code-index-tray.<hash>`.
- **Evidence:**
  - The running `p-indexing-tray` had started at 06:05. Reinstall replaced `~/.p/agent/indexing-service/bin/p-indexing-tray` at 06:10 and restarted the daemon, but the tray process was still the 06:05 one.
  - `startTrayLaunchdJob` reloaded the job only when the rendered plist differed from the file on disk, and otherwise ran plain `kickstart`, which starts an idle job and leaves a running one alone. The plist named the same binary path before and after the reinstall, so it never differed.
  - The linker writes the new build as a new file renamed over the old path, so the running tray keeps executing the old file (it did not crash with a code-signature error).
  - Two `swiftc -O` builds of the unchanged sources and the installed binary had the same SHA-256, so the build is byte-deterministic.
- **Approaches tried:**
  - **Attempt:** Record the binary's digest in a separate state file next to the plist and run `kickstart -k` when it differs.
    - **Outcome:** Did not work (rejected in design)
    - **Why:** A second record of what is loaded adds its own failure modes: writing the state after the restart risks a restart at every reconcile when the write fails, and writing it before risks losing the restart when `kickstart -k` fails.
  - **Attempt:** Restart the tray job from the install step after `installIndexingTray` builds a new binary.
    - **Outcome:** Did not work (rejected in design)
    - **Why:** The JavaScript installer would have to duplicate the label derivation, it misses a binary replaced outside reinstall, and it restarts the tray against the old daemon before the daemon restart.
  - **Attempt:** Put the binary's SHA-256 into the job definition (`P_INDEXING_TRAY_BINARY_SHA256` in `EnvironmentVariables`).
    - **Outcome:** Worked
    - **Why:** A new build becomes a changed definition, so the existing reload path (bootout, wait until launchd drops the job, write, bootstrap, and remove the plist when the bootstrap fails so the next attempt retries) restarts the tray exactly once, with no new state.
- **Root cause:** The job's identity covered the binary's path but not its contents, and `launchctl kickstart` without `-k` never restarts a running job.
- **Resolution:** `IndexingTrayManager` hashes the tray binary before any `launchctl` call and renders the digest into the plist. A changed binary reloads the job at the daemon restart that follows a reinstall, or at the next reconcile when the daemon kept running. Identical bytes leave the tray running. An unreadable binary reports no tray and leaves launchd alone until the next attempt. The first daemon start after this change reloads the job once, because the plist gains the new key.
- **Verification:** `indexing-tray-manager-macos.test.ts` reproduces the reinstall (a new file renamed over the binary path): the next daemon start reloads the job once and the following start only kickstarts; an unchanged binary and an identical rebuild only kickstart; a binary replaced under a running daemon reloads once at the next reconcile; a plist written before the digest existed reloads once; an unreadable binary makes no `launchctl` call, also after an earlier successful start, and the restored binary only kickstarts. `indexing-tray-launchd-job.test.ts` covers the digest (content-only, independent of inode and timestamps) and the job-level reload. The tests failed before the change with `kickstart` instead of a reload. Live check after `./reinstall.sh` of the fix: the first start of the new daemon reloaded the job once. The plist and `launchctl print` carried the digest of the installed binary, the job showed `runs = 1`, and the tray got a new pid. Fourteen minutes and at least two reconciles later, the same pid and `runs = 1` remained.
- **Prevention/follow-up:** Test trap found by the full suite: a manager test that deleted the installed tray binary passed in a fresh worktree but failed once `dist` existed. `resolveTrayCommand` then fell back to `packages/coding-agent/dist/bin/p-indexing-tray`. A test that removes or replaces the resolved binary must pin `resolveCommand`. Open: the daemon's shutdown sends the tray `SIGTERM` with `launchctl kill`, which should already have stopped the old tray during the reinstall's daemon restart. On the same machine a tray started at 06:23 was still running after a daemon start at 06:56. Why the shutdown signal did not stop it is not established.
- **Reusable learning:** When a launchd job (or any supervisor) is reconciled by comparing its definition, make the definition cover everything a restart must pick up, including the contents of a binary that is replaced at a fixed path. A plain `kickstart` never restarts a running job.
